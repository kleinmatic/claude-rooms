# v0.2 idea — MCP-native tools

**Status:** planned, not built. v0.1 works by shelling out to the `rooms` CLI
through the Bash tool. This documents the intended native path.

**Target revision: `2026-07-28`.** That revision landed after this design was
written and changed enough to matter — see [What 2026-07-28
changes](#what-2026-07-28-changes) at the end. The short version: it makes MCP
stateless, which turns the central architectural bet below into the protocol's
default rather than a workaround, and it replaces the notification mechanism we
had planned to test.

## Goal

Expose room operations as first-class **MCP tools** so an agent calls
`rooms_post({body})` directly instead of shelling out to `rooms post "..."`.

Why it's worth doing (fixes real problems, not just cosmetics):

- **Kills verb-guessing.** A CLI verb is invisible until guessed — which is why
  agents reached for `send`/`say` before finding `post`. An MCP tool has a name
  and a typed schema in the tool list; the agent can't guess wrong.
- **Structured I/O.** `read` returns JSON objects, not text parsed off a terminal.
- **Per-tool permissions** instead of blanket Bash permission.
- **No shell-quoting** issues (the `/rooms:post "$ARGUMENTS"` papercut).

## Decision: take one dependency, don't hand-roll

MCP is JSON-RPC 2.0 over stdio, so a hand-rolled ~150-line stdlib server is
possible and would keep the zero-install property. **We are deliberately NOT doing
that.** Owning bespoke protocol code means maintaining a thing that will be
forgotten and grow weeds. Instead: depend on the **official `mcp` Python SDK** —
a single external requirement that owns the wire format for us.

- Run it via **`uv` / `uvx`** so the dependency is fetched on demand into an
  isolated environment — nothing vendored into the repo, no global pip pollution.
- **Requirements:** Python **3.10+** (the SDK's floor; the v0.1 CLI stays 3.8+),
  and `uv` (or pip) available. Cross-platform: macOS, Linux, Windows — pure
  Python, prebuilt wheels for the transitive deps (pydantic, anyio).

## Architecture

- **Stateless stdio server, one per session.** All state lives in the shared
  maildir on disk, so each session can spawn its own cheap MCP server that just
  wraps the same directory. No shared process, no port — the same property that
  makes the filesystem design work makes stdio-per-session correct.
- **One core, two front doors.** Refactor the room logic out of `bin/rooms` into
  an importable module; the CLI and the MCP server both call it. No duplicated
  logic, no drift.
- **Bundle via the plugin's `.mcp.json`**, which launches the server with `uv`.

## Tools to expose

`open`, `list`, `join`, `leave`, `whoami`, `members`, `post`, `read`, `summary`,
`close` — the CRUD surface.

## What stays as-is

- **The CLI.** Humans use it, and it remains the source command for the Monitor
  waker (`rooms watch` / `rooms wait`).
- **The Monitor-based waker.** MCP tool calls are synchronous request/response and
  cannot wake an *idle* agent, so autonomous waking stays on the `Monitor` tool.

## What 2026-07-28 changes

**It validates the core bet.** MCP is now stateless: the `initialize` /
`notifications/initialized` handshake is gone, protocol version and client
capabilities ride in `_meta` on every request, and `Mcp-Session-Id` is removed.
"Stateless stdio server, one per session, all state on disk" stopped being a
clever workaround and became the protocol's own model, so the server gets
simpler than this doc assumed.

**It changes the waking question, and the answer is still Monitor.**
`resources/subscribe` no longer exists; opted-in server-to-client notifications
now flow over a single long-lived `subscriptions/listen` request, and that does
work on stdio — the server writes notifications tagged with
`io.modelcontextprotocol/subscriptionId` to stdout. But servers **MUST NOT**
write JSON-RPC requests at all now, and the Multi Round-Trip Requests pattern
replaced every server-initiated request (`sampling/createMessage`,
`elicitation/create`, `roots/list`) with a client retry. So the protocol can
notify but can no longer ask, and whether a notification becomes an *agent wake*
is a Claude Code harness question the spec doesn't address. Worth verifying
empirically someday; not worth designing around.

**New conformance work this phase has to do**, none of it hard: implement
`server/discover` (a MUST), put `resultType: "complete"` on every result, emit
`ttlMs` and `cacheScope` on `tools/list` and `resources/*` results, and return
tools in a deterministic order so client-side and prompt caches hit.

**Two deprecations worth knowing.** Logging is deprecated — log to `stderr`,
which stdio explicitly allows. Sampling is deprecated too, with the migration
being "integrate directly with LLM provider APIs," which forecloses ever having
the triage classifier or the room monitor borrow the client's model through MCP.
Shelling out to `claude -p` was already the right shape.

**Timing is now the real input.** The revision is days old, so the official
Python SDK will not implement it yet. Starting this phase against the previous
revision means writing an `initialize` handshake, session handling, and
`resources/subscribe` — three things `2026-07-28` deletes. Gate the start on SDK
support; nothing depends on this phase, so waiting is free.
